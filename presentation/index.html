Old model: Deploy = Release

A bug in production means a hotfix deployment, a rollback PR, an outage window. At 40k encounters per day, every minute of impact matters.
LaunchDarkly: Separate the two

Deploy whenever code is ready. Release when you're confident: the right users, in the right order. Roll back in seconds, not hours.
Here's the tension every one of these teams feels. Leadership wants features out the door faster, but remember, these are hospitals, and lives are genuinely on the line, so quality simply cannot slip. In the old world, deploying code and releasing a feature were the same single act, which means a bug in production turns into a frantic hotfix, a rollback pull request, and an outage window, and at forty thousand encounters a day every minute of that is enormously expensive. LaunchDarkly's whole premise is to break the link between deploying and releasing, and that is what the rest of this story is really about.

Separate Deployment from Release

🚀 Deploy

Merge and ship code to production anytime. The feature is wrapped in a flag; it doesn't activate. Providers see the existing workflow.

🎯 Release

Toggle the flag when you're ready: internal testers first, then specific departments, then every hospital. No deployment.

⚡ Rollback

Something went wrong? Toggle the flag off. Users see the old experience in under a second: no hotfix, no rollback PR, no outage window.

This is how Helix ships at speed, without increasing risk to providers or patients.
The idea is simple to say and surprisingly powerful in practice: separate deployment from release. Deploying code becomes a quiet technical event, because the feature ships to production wrapped in a flag that's switched off, so nobody sees it yet. Releasing then becomes a business decision you make later, on your own terms: turn it on for your internal testers, then one department, then every hospital, all from the dashboard. And if something goes wrong, rolling back is just flipping that same switch off, so the old experience is back in under a second, with no hotfix and no outage window.

Part 1: Release

Instant Flag Updates: No Page Reload

When the flag changes in the LD dashboard, every connected browser knows in under one second.

# Python: register a flag-change listener
def on_change(event):
    payload = json.dumps({
        "flag": "helix-auto-scribe",
        "value": event.current_value,
    })
    for q in _sse_queues:        # fan out
        q.put_nowait(payload)

ld.get_flag_tracker() \
  .add_flag_value_change_listener(
    "helix-auto-scribe", ctx, on_change)
// Browser: EventSource (SSE)
const es = new EventSource(
  "http://localhost:8000/events");

es.onmessage = (e) => {
  const { flag, value } = JSON.parse(e.data);
  if (flag === "helix-auto-scribe")
    panel.hidden = !value;   // no reload
};
LD SDK fires a server-side callback → asyncio queue → SSE stream → browser reacts.
Now, how does the feature appear the very moment we flip the flag, without anyone refreshing their browser? On the server side, the LaunchDarkly SDK holds a streaming connection open to LaunchDarkly and fires a callback within milliseconds of any change. We catch that callback and push it straight out to the browser over Server-Sent Events. The browser is already listening on that stream, so when the value flips, the panel simply appears or disappears on its own. No polling, no reload, under a second from end to end.

Part 1: Remediate

Something Went Wrong

Incident: the AI is over-coding routine visits as high-complexity (CPT 99285). Compliance flagged it — every minute of exposure is liability.
Option A — Dashboard: toggle helix-auto-scribe OFF (~10s).  ·  Option B — REST API: one semantic-patch call — curl, Postman, or your monitoring tool. 
curl -X PATCH "https://app.launchdarkly.com/api/v2/flags/default/helix-auto-scribe" \
  -H "Authorization: $LD_API_TOKEN" \
  -H "Content-Type: application/json; domain-model=launchdarkly.semanticpatch" \
  -d '{"environmentKey":"test","instructions":[{"kind":"turnFlagOff"}]}'
Result: flag off, providers back on the manual workflow — no deployment, no rollback PR, no outage. Resolved in seconds. Wire the call into PagerDuty or Datadog for automated rollback on alert.
But this is healthcare, so let's talk about what happens when it goes wrong. Imagine compliance discovers the AI is over-coding, billing routine visits as high-complexity, and every extra minute it stays live is a growing liability. In the old world this is a fire drill. Here I have two easy options. I can flip the flag off in the dashboard in about ten seconds, or I can do it from a script, one REST call from curl, from Postman, or even straight from a monitoring tool like Datadog or PagerDuty, so the rollback happens automatically the instant an alert fires. Either way the feature is gone in seconds, providers are back on the safe manual workflow, and there was no hotfix, no rollback pull request, and no outage window.

How the Go SDK Evaluates It

// Build a context for this clinician
ctx := ldcontext.NewBuilder(userID).
    SetString("department", department).
    SetString("role", role).Build()

// Evaluate the flag — value AND reason
detail, _ := ldClient.BoolVariationDetail(
    "helix-maternity-pathway", ctx, false)

if detail.Value {
    renderMaternityPathway()  // new module
} else {
    renderStandardChart()     // everyone else
}
Same one-flag pattern as Part 1, server-side in Go. The context carries department (plus any extra attributes you want along for the ride); LD checks it against the rule and answers for this clinician.
BoolVariationDetail also returns the reason — RULE_MATCH / FALLTHROUGH — so you can answer "why did this user see this?" It's shown in the demo's evaluation-detail drawer.
Under the hood it's the same one-flag pattern as Part 1, just written in Go this time. We build a context describing the clinician, really just their department, and ask LaunchDarkly to evaluate the flag for them. If it comes back true we render the pathway, otherwise the standard chart. One detail I love: the SDK doesn't only tell us the answer, it tells us the reason, RULE_MATCH or FALLTHROUGH, which we surface in the demo so you can always answer the question "why did this person see this?". And notice the default is false, so if LaunchDarkly were ever unreachable, every clinician safely falls back to the standard chart.

Part 3: Java SDK

Configuration, Not Just On/Off

A flag can carry a value, not only a switch. A developer builds the alert; the clinical team owns the threshold from the dashboard.

// Alert logic is in code; the THRESHOLD
// is a LaunchDarkly Number flag
LDContext ctx = LDContext
    .builder("helix-clinical-platform").build();

int threshold = ldClient.intVariation(
    "helix-bp-alert-threshold", ctx, 140);

boolean alert = reading >= threshold;
// clinical team re-tunes it in the dashboard
The "wow," in seconds:

1. Enter 135 mmHg → NORMAL (threshold 140)
2. Lower helix-bp-alert-threshold to 130 in LD
3. Check 135 again → ALERT
Flags aren't only on/off. A Number (or string, or JSON) flag lets non-engineers tune real behaviour safely, with no deploy.
There's one more shape a flag can take that people often miss: it doesn't have to be a simple on or off. For Part 3, a developer built a blood-pressure alert, the kind of thing that screens for preeclampsia, but the threshold it fires at isn't baked into the code. It's a LaunchDarkly Number flag that the clinical team owns. Watch: I enter a reading of 135, and against the default threshold of 140 it comes back normal. Now I lower that threshold in the dashboard to 130, check the very same 135 again, and it flips to an alert, with no deploy and no restart; the Java service simply read the new number. The takeaway is that flags aren't only switches. A number, a string, or even a JSON blob can let the people closest to the problem tune real behaviour safely, without an engineering ticket every single time.

"My Baby at 2am"

Scenario: A first-time parent. 3am. Their 3-week-old has a fever of 100.8°F and won't stop crying — rush to the ER, or wait until morning?
HELIX-PARENT gives warm, evidence-based guidance and says clearly when to call 911. A boolean flag, helix-parent-connect, gates the feature: toggle it off and parents fall back to the 24/7 nurse line. 
# Escalation heuristic: detect an emergency
escalate = any(w in content.lower() for w in
    ["911", "emergency room", "go to the ed"])

# Feature flag gates the AI; off = nurse line
if not ld.variation("helix-parent-connect",
                    ctx, True):
    return {
        "response": "Our AI assistant is off. "
            "Call the 24/7 nurse line: "
            "1-800-HELIX-RN.",
        "escalate": False,
    }
Let me make that concrete with my favourite example. AI Config

Control your AI models and prompts from the LaunchDarkly dashboard

Flag: helix-clinical-ai  ·  Type: AI Config  ·  SDK: Python + LD AI SDK
Finally, Part 5: how do you manage AI responsibly? Helix runs three different clinical AI personas, and today every prompt tweak or model change is a code change and a deployment. LaunchDarkly's AI Config is built for exactly this; the helix-clinical-ai config controls the model and the prompt from the dashboard.
Part 5: The Problem

AI Prompts Shouldn't Live in Code

Without AI Config:

▸ System prompt is a string constant in main.py
▸ Improve the prompt → open a PR, code review, deploy
▸ Upgrade the model → another full deployment
▸ A/B test prompts → branching logic in code
▸ 3 clinical personas → 3 code paths to maintain
With AI Config (AgentControl):

▸ Model + system prompt live in the LD dashboard
▸ Update the prompt → next API call uses it, zero deploy
▸ Swap models without touching code
▸ Route contexts to different AI configurations
▸ Track token usage + success rates per variation
Think about what it means to have your AI prompts living in code. The system prompt is just a string constant sitting in main.py. Want to improve it after an accuracy review? That's a pull request, a code review, and a deploy. Want to upgrade the model, or A/B test two prompts, or run three different personas? That's more branches and more code paths to maintain. With AI Config, the model and the prompt move out of the code and into the LaunchDarkly dashboard, so you change them there and the very next API call uses the new version, with no deploy and no waiting on engineering.

Part 5: Integration

One Code Path. Many Configurations.

from ldai.client import LDAIClient, AIConfig
ai_client = LDAIClient(ld)            # wraps your existing LD client

# The "department" attribute routes to the right AI Config variation
context = Context.builder(user_key).set("department", "ed").build()

# Model name AND system prompt come from the LaunchDarkly dashboard
ai_config, tracker = ai_client.config(
    "helix-clinical-ai", context, AIConfig(enabled=False)
)

response = anthropic_client.messages.create(
    model=ai_config.model.name,            # ← e.g. claude-haiku-4-5
    system=ai_config.messages[0].content,  # ← prompt owned in LD
    messages=[{"role": "user", "content": transcript}],
)
tracker.track_success()                    # ← usage tracked back to LD
The code behind all of that is almost anticlimactic, which is exactly the point. You make one call to fetch the AI config, and LaunchDarkly hands back the right model and the right prompt for this context. You pass them to the model, then report token usage and success back to LaunchDarkly so you can see cost and reliability per variation. The application code itself never changes; the model and the prompt are controlled entirely from the dashboard.
