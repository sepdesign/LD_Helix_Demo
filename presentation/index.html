Old model: Deploy = Release

A bug in production means a hotfix deployment, a rollback PR, an outage window. At 40k encounters per day, every minute of impact matters.
LaunchDarkly: Separate the two

Deploy whenever code is ready. Release when you're confident: the right users, in the right order. Roll back in seconds, not hours.
This is the core tension in clinical software development. The old model couples deployment and release: ship the code and the feature goes live simultaneously. If something goes wrong, you're scrambling. LaunchDarkly breaks that coupling. Code goes to production whenever it's ready. The feature activates only when you choose. And if something goes wrong, you turn it off in seconds with no deployment needed.

Separate Deployment from Release

🚀 Deploy

Merge and ship code to production anytime. The feature is wrapped in a flag; it doesn't activate. Providers see the existing workflow.

🎯 Release

Toggle the flag when you're ready: internal testers first, then specific departments, then every hospital. No deployment.

⚡ Rollback

Something went wrong? Toggle the flag off. Users see the old experience in under a second: no hotfix, no rollback PR, no outage window.

This is how Helix ships at speed, without increasing risk to providers or patients.
Deployment is a technical event: when code goes to a server. Release is a business decision: when users see the feature. LaunchDarkly lets you separate them completely. You can deploy every day, multiple times a day, with zero new features going live until you choose. Then release on your schedule, to the right users, with an instant rollback path always available.

Instant Flag Updates: No Page Reload

When the flag changes in the LD dashboard, every connected browser knows in under one second.

# Python — register a flag change listener
def _on_flag_change(event):
    payload = json.dumps({
        "flag": "helix-auto-scribe",
        "value": event.current_value
    })
    for q in _sse_queues:
        loop.call_soon_threadsafe(
            q.put_nowait, payload
        )

ld.get_flag_tracker()\
  .add_flag_value_change_listener(
    "helix-auto-scribe",
    system_ctx,
    _on_flag_change   # fires on change
)
// Browser — EventSource (SSE)
const es = new EventSource(
  "http://localhost:8000/events"
);

es.onmessage = (e) => {
  const { flag, value } =
    JSON.parse(e.data);

  if (flag === "helix-auto-scribe") {
    // No page reload — panel
    // appears or hides instantly
    panel.hidden = !value;
  }
};
LD SDK fires a server-side callback → asyncio queue → SSE stream → browser reacts.
This is one of the most visually compelling parts of the demo. The LD server-side SDK maintains a persistent streaming connection to LaunchDarkly. When the flag changes, it fires a Python callback on the server. We push that onto an asyncio queue. The FastAPI SSE endpoint streams that queue to every connected browser. Toggle the flag → browser updates in under a second, with no page refresh.

Part 1: Remediate

Something Went Wrong

Incident: The AI is generating CPT 99285 (high-complexity E&M) for routine visits. Claims are being over-coded. Compliance has flagged it. Every additional minute of exposure increases liability.

Option A: Manual toggle

LD dashboard → helix-auto-scribe → OFF.
Takes under 10 seconds.

Option B: Flag trigger (automated)

LD generates a webhook URL for the flag.
POST to it from any monitoring system (or via curl).

curl -X POST \
  "https://app.launchdarkly.com/\
api/v1/flags/triggers/YOUR_URL"
Result:

Flag is off. Providers see the manual workflow. No deployment. No rollback PR. No hotfix branch. No outage window. Incident resolved in seconds.
Wire this trigger URL into PagerDuty, Datadog, or any monitoring tool for fully automated rollback on alert.
This is the "oh no" moment. In the old world, you're scrambling: hotfix branch, code review, deploy, coordinate with DevOps, wake up on-call, update the runbook. With LaunchDarkly, you toggle the flag off. The Remediate card in the demo dashboard has a curl command. Run it and watch the panel disappear instantly. In production, you'd wire this trigger URL to your monitoring system for automatic rollback when an alert fires. The flag is your safety net.

Context Attributes

Contexts carry the attributes LaunchDarkly uses when evaluating targeting rules.

// Go — build the evaluation context
ctx := ldcontext.NewBuilder(userID).
    SetString("department",   department).
    SetString("role",         role).
    SetString("hospitalTier", hospitalTier).
    SetBool("hasBirthCenter", hasBirthCenter).
    Build()

// BoolVariationDetail returns value + reason
detail, _ := ldClient.BoolVariationDetail(
    "helix-maternity-pathway",
    ctx,
    false, // default
)

// detail.Value       — true / false
// detail.Reason.Kind — TARGET_MATCH
//                    — RULE_MATCH
//                    — FALLTHROUGH
Attributes on the context:

userId: provider key (email)
department: maternity | ed | icu
role: attending | charge_nurse
hospitalTier: level1 | level2
hasBirthCenter: true | false
BoolVariationDetail returns the flag value and the reason, so you can surface exactly which targeting rule matched in your UI.
The context is the "who" in every flag evaluation. We're sending five attributes. The Go service uses BoolVariationDetail instead of BoolVariation, which gives us the evaluation reason alongside the value. We surface this reason in the demo UI so you can see in real-time which targeting rule is responsible for each outcome.

Multi-Context: Java

Evaluate Multiple Contexts Simultaneously

A provider's access can depend on who they are AND what organization they belong to.

// User context — the individual provider
LDContext userCtx = LDContext
    .builder(ContextKind.of("user"), userId)
    .set("role", role)
    .set("department", department)
    .build();

// Organisation context — the hospital
LDContext orgCtx = LDContext
    .builder(ContextKind.of("organization"), orgId)
    .set("plan", orgPlan)         // "enterprise"
    .set("hasBirthCenter", true)
    .build();

// LD evaluates targeting rules against
// BOTH contexts simultaneously
LDContext multi =
    LDContext.createMulti(userCtx, orgCtx);

boolean enabled = ldClient.boolVariation(
    "helix-maternity-pathway", multi, false
);
Enterprise pattern:

Floor nurse at a general hospital
→ false

Same floor nurse at an enterprise-plan hospital with a birth center
→ true

The organization context unlocked what the user context alone couldn't.
Multi-context is a powerful enterprise pattern. You're not evaluating against just the individual; you're simultaneously evaluating against the organization they belong to. An enterprise hospital can unlock the maternity pathway for all its providers, even those who wouldn't qualify by role alone. You can write rules targeting organization.plan or user.role, or combine them. This is how B2B SaaS companies do entitlements at scale.

Experimentation

Data-Driven Release Decisions

1. Create a Metric

LD Experimentation → key: maternity-pathway-engaged. This is the conversion event you'll measure across flag variations.

2. Attach to the Flag

Create an experiment on helix-maternity-pathway. LD automatically buckets users into control and treatment groups.

3. Track & Decide

Fire the event when providers engage. LD attributes it to the correct variation. Get statistically significant results, then decide.

// Track a conversion event.
// LD attributes this to the correct
// flag variation automatically.
ldClient.trackMetric(
    "maternity-pathway-engaged",
    ctx,
    1.0   // optional numeric value
);

// Non-blocking — LD buffers
// and flushes in the background
Get statistically significant results. Roll out to everyone (or roll back) based on evidence, not gut feel.
The experimentation workflow is elegant. Create a metric, attach it to the flag, and call trackMetric whenever a meaningful action occurs. LD does the attribution: it knows which variation each user was in when they fired the event. After enough data, you get a statistically significant result. Then you make a data-driven decision: roll out to everyone or pull back. No custom analytics pipeline required.

AI Config is the most forward-looking capability in this demo. The Clinical AI team has three different AI personas serving different clinical contexts. Without LaunchDarkly, every prompt change is a deployment. Let's fix that.
AI Config: The Problem

AI Prompts Shouldn't Live in Code

Without AI Config:

▸ System prompt is a string constant in main.py
▸ Improve the prompt → open a PR, code review, deploy
▸ Upgrade the model → another full deployment
▸ A/B test prompts → branching logic in code
▸ 3 clinical personas → 3 code paths to maintain
With AI Config (AgentControl):

▸ Model + system prompt live in the LD dashboard
▸ Update the prompt → next API call uses it, zero deploy
▸ Swap models without touching code
▸ Route contexts to different AI configurations
▸ Track token usage + success rates per variation
In clinical AI, you iterate on prompts constantly. The ED coding prompt needs tuning after a billing audit. The OB prompt needs updates after a clinical accuracy review. With prompts hardcoded in Python, every change is a deployment: code review, test, deploy, monitor. With AI Config, you update the prompt in the dashboard and the next API call uses it. No deploy, no PR, no waiting.

AI Config: Integration

One Code Path. Many Configurations.

from ldai.client import LDAIClient, AIConfig

ai_client = LDAIClient(ld)   # wraps your existing LD client

# Context attribute routes to the right AI Config variation
context = Context.builder(user_key).set("department", "ed").build()

# Model name and system prompt come from the LaunchDarkly dashboard
ai_config, tracker = ai_client.config(
    "helix-clinical-ai",
    context,
    AIConfig(enabled=False)   # safe fallback if flag is off
)

model_name    = ai_config.model.name   # "claude-haiku-4-5-20251001"
system_prompt = next(
    (m.content for m in ai_config.messages if m.role == "system"),
    "Default fallback prompt"
)

response = anthropic_client.messages.create(
    model=model_name,
    max_tokens=1024,
    system=system_prompt,              # ← controlled from LD dashboard
    messages=[{"role": "user", "content": transcript}]
)

tracker.track_success()                # ← usage tracked back to LaunchDarkly
tracker.track_tokens(input_tokens=response.usage.input_tokens,
                     output_tokens=response.usage.output_tokens)
This is the key pattern. One call to ai_client.config(): the model name and system prompt come back from LaunchDarkly based on the context. We extract them, pass them to Anthropic, and track usage back to LD. Change the model or prompt in the dashboard and the next call picks it up automatically. The application code never needs to change. This is how you do responsible AI deployment.
AI Config: Parent Connect

"My Baby at 2am"

Scenario: A first-time parent. 3am. Their 3-week-old has a fever of 100.8°F and won't stop crying. They don't know whether to rush to the ER or wait until morning.
HELIX-PARENT responds with warm, evidence-based guidance: references AAP guidelines, explains what to watch for, tells them clearly when to call 911.

If the response detects an emergency, an escalation flag triggers the nurse line workflow. If the AI feature is off for any reason, the fallback is the 24/7 nurse line. Parents are never left without support. 
# Simple escalation heuristic
escalate = any(
    w in content.lower()
    for w in [
        "911",
        "emergency room",
        "call 911",
        "go to the ed"
    ]
)

# Graceful fallback when
# flag is OFF
if not ai_config.enabled:
    return {
        "response": (
            "Our AI assistant is "
            "temporarily unavailable. "
            "Please call our 24/7 "
            "nurse line at "
            "1-800-HELIX-RN."
        ),
        "escalate": False
    }
Parent Connect is the emotional core of this demo. It's 3am. A new parent is scared. HELIX-PARENT responds: warm, clear, evidence-based. We have a simple escalation heuristic: if the AI response mentions 911 or the emergency room, we flag it for the UI to show the nurse line prominently. And if the feature flag is off for any reason, we fail gracefully to the 24/7 nurse line. The parent always has someone to talk to. Safety is never compromised.
